# תהליך המלצת כלים — VOVAX Company-Wide

## עקרון מנחה
כל מנהל מחלקה ב-VOVAX מכיר את הבעיות האמיתיות בתחומו טוב יותר מסריקה כללית. המלצות כלים
מגיעות מהשטח — מניסיון תפעולי אמיתי — לא מדוחות כלליים בלבד.

## ארבעה שלבים קבועים

### שלב 1 — זיהוי ורישום (כל מנהל)
מתי לדווח: כשכלי יכול לפתור בעיה אמיתית שהכלים הקיימים לא פותרים.
לא לדווח על: "נשמע מעניין" / כלי שמשכפל כלי קיים / ניסוי Labs שאין לו תיעוד API.

**פורמט חובה:**
```
כלי: [שם + URL/מקור אמיתי — לא ניחוש]
מנהל מגיש: [שם]
מחלקה: [שם המחלקה]
בעיה שנפתרת: [תיאור קצר וספציפי — מה לא עובד עכשיו]
למה הכלים הקיימים לא מכסים זאת: [הסבר ספציפי]
עלות משוערת: [אם ידועה — מקור תיעוד רשמי]
```

### שלב 2 — הערכה טכנית (אריאל + צוות Engineering)
אריאל בודק ארבעה ממדים:
1. **כפילות** — האם כלי קיים כבר מכסה זאת? (תקדים: n8n נדחה כי Zapier קיים)
2. **עלות אינטגרציה** — כמה זמן פיתוח להחיב ל-Railway stack
3. **אמינות** — תיעוד API אמיתי? רמת Stability? לא Labs experiment
4. **אבטחה** — עמידה בעקרון מינימום הרשאה ובתקנון החברה

פלט: המלצת "לאמץ / לדחות / לשקול מחדש" עם נימוק.

### שלב 3 — הערכת עלות (נטע)
נטע מחשבת עלות חודשית/שנתית ממקור רשמי (לא הערכה), מריצה ניתוח "בנה-או-קנה",
ומכינה שורה למרשם העלויות (`references/cost-ledger.md`) לפני ההחלטה הסופית.

### שלב 4 — החלטה ותיעוד (אלון)
כל החלטה — אומצה או נדחתה — נרשמת אצל אלון:

```
תאריך: YYYY-MM-DD
כלי: [שם + URL]
מגיש: [מנהל + מחלקה]
בעיה שנפתרת: [תיאור קצר]
הערכת אריאל: [תמצית ממצאים טכניים]
עלות: [נטע — חודשי/שנתי]
החלטה: אומץ / נדחה
סיבה: [מה הוחלט ולמה]
אחראי אינטגרציה: [שם אם אומץ]
```

**למה מתעדים גם דחייה:** כדי שמנהל עתידי לא יציע שוב אותו כלי — הרציונל נשמר.

## מה לא חלק מהתהליך הזה
- כלים שאריאל מוצא ביוזמתו (אלה נכנסים ישירות דרך המנדט הקבוע של אריאל)
- החלפת כלי קיים ב-scope קריטי (Production, Publishing) — זה שינוי תשתיתי שדורש דיון נפרד
- שכר/גיוס — זה עינב
